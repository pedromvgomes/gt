## Highlights

- **Coverage artifacts now mirror the repository.** The bulwark stage copies the
  whole `gt-coverage` tree into the scan root instead of lifting two named files
  out of it, so `coverage.source: report` finally works for a repository with
  more than one module or package per language.
- **Dependabot `allow:` rules.** A pin held indirectly is never bumped by
  default, and `.gt-repo.yaml` could not say otherwise — so syncing a repository
  that relied on an allow rule silently froze it.
- **A merge no longer re-runs the pipeline.** The coverage stages stopped being
  forced on every push now that bulwark keys baselines by tree, so an
  already-validated push skips every stage again.
- **The merge token is minted from the App's client id.**
  `actions/create-github-app-token` deprecated `app-id`, so the secret becomes
  `APP_CLIENT_ID` — and opting into `github_app` without it now fails loudly
  instead of quietly falling back to a token that cannot do the job.

## Action required: `APP_CLIENT_ID`

Any repository with `dependabot_auto_merge.github_app: true` needs an
`APP_CLIENT_ID` secret (an organisation secret is fine). The client id is on the
GitHub App's settings page; `APP_PRIVATE_KEY` is unchanged.

Until it is set, the auto-merge job fails with:

```
::error::dependabot_auto_merge.github_app is true but APP_CLIENT_ID is not set.
```

That failure is the point. Previously a missing `APP_ID` skipped the mint step
and carried on with `GITHUB_TOKEN` — which cannot merge a PR that touches
`.github/workflows/**`, and being unable to merge those is the entire reason the
opt-in exists. A green run that silently does the thing the setting exists to
prevent is worse than a red one.

Set `github_app: false` to merge with `GITHUB_TOKEN` and accept that limitation.

## Dependabot `allow:` rules

Dependabot's default is direct dependencies only. Anything a repository holds
*indirectly* is never bumped unless an allow rule says so, and `.gt-repo.yaml`
had no way to express one — so the first `gt repo sync` dropped the rule and
froze the pin.

```yaml
dependabot:
  - ecosystem: gomod
    directory: /internal/golang/go-pin
    allow:
      - dependency_name: github.com/securego/gosec/v2
        dependency_type: all
```

Either field may stand alone — a name, a type, or both. A rule with neither is
rejected rather than rendered: it matches nothing, which Dependabot reads as
"update nothing", and an entry with no rules emits no `allow:` key at all.

This came from bulwark, where the consequence was as bad as it gets. Its
`go-pin` module exists so its **gosec and govulncheck** pins are visible to
Dependabot rather than frozen in Go constants. The module has no `.go` files, so
`go mod tidy` marks both pins `// indirect`; without the allow rule neither is
ever bumped. Nothing reports that — a dependency that stops being updated
produces no signal, and bulwark's own `pins_test.go` only fires *after* a bump
lands. A security scanner running years-old tools keeps printing `[PASS]`.

It is the third gap of this shape, after `groups:` and `applies-to`. They share
one lesson worth stating plainly: **anything the spec cannot express disappears
on the first sync, and the diff looks clean because the file is generated.**
Parse the old and new `dependabot.yml` and diff on `(ecosystem, directory)`
before committing an onboarding.

## A merge no longer re-runs the pipeline

v1.0.0 forced `preflight`, `build`, `test` and `bulwark` to run on every push to
the default branch. That was necessary at the time: bulwark took its coverage
baseline from a run on the merge-base, and skipping it left the gate comparing
numbers produced by different methods — main measured at 0.7% against pull
requests at 76.2%, which no regression could trip.

bulwark v1.8.0 keys baselines by **tree**. A pull request records its own
measurement, and a squash merge lands a commit carrying that same tree, so the
number main needs is already there — measured by the pipeline that knows how to
measure it, minutes earlier.

So the exemption is gone and `attest` has its full value back: an
**already-validated push skips every stage**.

Requires bulwark `v1.8.0` or later. On an older bulwark the baseline falls back
to being recomputed in a bare worktree, which for a `coverage.source: report`
repository measures the wrong thing or nothing at all.

## Coverage artifacts mirror the repository

`ci-test.yml` uploads an artifact named `gt-coverage`, and the bulwark stage
places it where bulwark looks. That placement used to copy exactly two files —
`coverage.out` and `lcov.info` — to the scan root.

bulwark does not look for reports at one agreed path. It looks next to the unit
that produced each one:

| Language | Where bulwark looks | Override |
|---|---|---|
| Go | `<moduleDir>/coverage.out` | `coverage.go.report` |
| Rust | `<crateDir>/coverage/{llvm-cov.json,lcov.info}` | `coverage.rust.{report,lcov}` |
| TypeScript | `<packageDir>/coverage/{coverage-summary.json,lcov.info}` | none, deliberately |

TypeScript has no override because those locations are Vitest convention rather
than a project's choice — so no configuration could rescue a flat copy. A
monorepo with two TypeScript packages had nowhere to put the second one's
report, and `coverage.source: report` there did not fail: bulwark found no
per-package reports, marked the language unmeasured, and warned. A warning
inside a green pipeline is not a signal, so the visible outcome was a coverage
gate that had quietly stopped covering a language. Repositories hitting this
were abandoning the reusable workflow and hand-rolling a bulwark job that
restored the reports themselves.

The stage now mirrors the artifact's tree into the scan root, which is what the
contract already said — "an artifact containing whatever profiles it produced".
Lay the artifact out the way the repository is laid out and every report lands
where discovery already looks. Every placed path is echoed, because a step that
writes into the tree about to be scanned has to be answerable from its log, and
a report one directory away from where bulwark looks is otherwise
indistinguishable from one that was never produced.

**Nothing to change if you are already on `report`.** An artifact holding only
`coverage.out` or `lcov.info` at its top level still lands at the scan root,
byte for byte where the flat copy left it.

## Upgrading

Nothing to pin: governed repositories track `@v1`, which this release moves.

Pair it with bulwark `v1.8.0` or later, for the tree-keyed baselines the skip
above depends on.

Repositories still on `coverage.source: run` can now flip to `report` by having
`ci-test.yml` upload `gt-coverage` with paths that mirror the repository —
`gt repo sync` does not do this for you, because what a repository's test suite
produces is its own to declare.
