## Highlights

- **`gt repo` — repo governance as a gt subsystem.** One committed
  `.gt-repo.yaml` per repository drives its Dependabot config, a
  `ci-orchestration`/`cd-orchestration` pipeline, conventional-commit
  enforcement, bulwark, Dependabot auto-merge, and a weekly drift-sync.
  `gt repo check` answers "is this repository compliant?", `gt repo sync`
  fixes it, and `gt repo fleet` does both across an owner.
- **A moving `v1` tag.** Governed repositories pin gt's reusable workflows to
  `@v1`, so gate logic changes reach every repository without editing a single
  file. This release is what creates that tag; `release.yml` moves it on every
  future release and fails loudly if the move does not take.
- **1.0 because other repositories now depend on this.** Eleven of them pin
  `pedromvgomes/gt@v1`. That is a compatibility promise, and the version
  should say so.

## Why this exists

Keeping ten-odd repositories structurally consistent was manual and drifting.
Dependabot configs had diverged, several had none, PR gating was bespoke per
repository, and conventional-commit enforcement was inconsistent.

A template repository is the wrong tool: templates copy once and never
propagate, and these repositories are genuinely heterogeneous — Rust, Go, yarn
and pnpm workspaces, Python, Terraform — with hand-tuned configs worth
preserving. What was needed is bootstrap for new repositories *and* verify/fix
for existing ones, from one source of truth.

## How it propagates

| Layer | Mechanism | Propagates by |
|---|---|---|
| Gate logic, conventional commits, drift check | Reusable workflows in this repository, called via a thin pinned caller | reference — the moving `v1` tag, zero file changes |
| Files that must exist in-repo | Rendered from templates embedded in the binary | `gt repo sync` |
| GitHub API state | `gh api`, driven by the same file | `gt repo settings apply` |

The moving tag is not a stylistic choice. GitHub hard-blocks `GITHUB_TOKEN`
from writing anything under `.github/workflows/`, so if gt rendered full gate
logic into each repository, every logic change would rewrite workflow files
everywhere and the weekly sync would need a long-lived `workflows:write` PAT
across every org. With a thin caller pinned to `@v1`, gate logic changes need
no file change at all.

## The pipeline

Branch protection requires exactly one check: `ci-gate`. Every stage is a job
in one workflow, so aggregation is `needs:` and `needs.*.result` — no polling,
no timeout to tune, and no way to confuse "absent" with "not started yet". A
skipped stage passes, which is the point of `ci-preflight`.

`ci-orchestration.yml` and `cd-orchestration.yml` are **managed**: gt owns them
and rewrites drift. The `ci-*`/`cd-*` stages are **scaffolds**: gt creates each
once and then never modifies or deletes it, because doing either would destroy
code gt did not write.

A tree that passes the gate is attested, so a push that merely squashed an
already-validated PR skips every stage, and `cd-orchestration` can refuse to
ship a tree that never passed.

## Commands

```
gt repo init          # detect ecosystems, write .gt-repo.yaml
gt repo check         # report drift; non-zero exit when non-compliant
gt repo sync          # write the governance files the spec declares
gt repo config        # print the resolved spec, defaults applied
gt repo settings      # diff or apply the GitHub settings gt manages
gt repo fleet         # check, sync or merge-pending across an owner
```

## Upgrading from v0.6.0

Nothing in `gt clone`, `gt wt`, `gt setup`, `gt config` or `gt setauth`
changed. Existing configs and worktree layouts are untouched, and `gt repo` is
additive — a repository without a `.gt-repo.yaml` is simply not governed.

Two changes are worth knowing about if you inspect gt's own files:

- gt now writes its config, update state and `.envrc` at `0600` (directories
  `0700`) rather than `0644`/`0755`. Existing files are not re-permissioned;
  the change applies as they are rewritten.
- gt builds on Go 1.26.6, pinned via `toolchain` in `go.mod`.

## Security

This release fixes what gt's own bulwark stage found once it started scanning
gt:

- **Go 1.26.6.** 18 stdlib advisories, none in gt's code. `go-version: "1.26"`
  resolves to 1.26.0 and stays there; `go.mod` now carries
  `toolchain go1.26.6` and every workflow reads `go-version-file: go.mod`, so
  there is one place to bump rather than three that can disagree.
- **No `curl … install.sh | sh` in CI.** `install.sh` verifies the checksum of
  the binary it downloads but cannot vouch for itself — it was fetched
  unpinned from `main` and piped into a shell, in every governed repository's
  CI, holding tokens with write access. The reusable workflows now use
  `gh release download` and verify the checksum with code that arrived with
  the workflow. `install.sh` itself is unchanged: piping it is reasonable
  ergonomics for a human choosing to trust the project, which is a different
  decision from CI doing it unattended in someone else's repository.
- **Bounded extraction.** `gt update` extracts the release tarball through
  `io.CopyN` with a 512 MiB cap. The archive's checksum is verified first, so
  a decompression bomb would need a release that is both malicious and
  correctly checksummed — but a limit is a stronger guarantee than "we checked
  earlier".

The remaining scanner findings are annotated line by line with the reason they
are not defects — a tool that reads user-named paths and shells out to git
produces a lot of them. No rule is disabled globally, so the next genuine
finding in the same file still surfaces.
