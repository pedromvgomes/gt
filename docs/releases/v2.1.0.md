## Highlights

- **A `.gt-repo.yaml` with an unknown key now fails to parse, instead of
  silently resolving to the default spec.** `repospec.Parse` decodes with
  `KnownFields(true)`, recursively. A typo in a key name, or a key retired
  from a previous release, used to parse clean and hand back whatever the
  default happened to be for that field — a manifest whose author believed a
  setting was in force while gt quietly ignored it. It now fails the parse
  and names the offending field. **No governed repository has exercised this
  path before**: any manifest carrying a key gt has never recognized —
  a misspelling, a key from a fork, leftover YAML — starts failing
  `gt repo check` and `gt repo settings apply` on this release, where it
  previously passed. The one exception is `require_up_to_date`, the retired
  spelling of `base_freshness`: it still parses, and still resolves to
  `auto`, because every value it could ever have held already computes to
  `auto` on this release's `base_freshness`.
- **`lydite-clearance.yml` is `gt-lydite-clearance.yml`.** The rendered
  filename doubles as part of the `uses:` ref gt's own repository resolves
  its reusable workflow through, and collided with a name lydite's own
  `lydite/actions` repository also publishes. A repository that already
  synced the old filename keeps it until its next `gt repo fleet sync` —
  nothing deletes an unmanaged file on its own.
- **A repository with `lydite.coverage: true` gets a coverage baseline
  recorded on every push to its default branch**, via a new
  `reusable-lydite-baseline.yml` stage gated on `LyditeCoverage`, not merely
  on `lydite` being enabled. A repository with coverage off gets none of it,
  the same as before.
- **`lydite:` takes a `relay` key.** Set, it names the identity
  `reusable-lydite.yml` and `reusable-lydite-clearance.yml` forward as their
  `relay` input to lydite's own scan and clearance workflows. Left unset, a
  repository with `lydite` enabled gets `GT_LYDITE_RELAY` written as a
  repository Actions variable by `gt repo settings apply`, and both reusable
  workflows fall back to that variable whenever the caller passes no
  explicit `relay` input. Comments and clearance replies post under a real
  relay identity by default now, rather than `github-actions[bot]`.

## The strict spec parse

```yaml
lydite:
  enabled: true
  covearge: true   # typo — this now fails Parse, naming the field
```

Before this release, that document decoded to the default spec: `coverage`
kept its zero value, and nothing said so. `gt repo check` reported a clean
tree for a repository that believed coverage was configured and was not.

`Parse` now runs `yaml.NewDecoder` with `KnownFields(true)` instead of a
plain `yaml.Unmarshal`, and treats an empty document (`io.EOF` from the
decoder) as the defaults standing, same as before. Every other decode error,
including an unrecognized field anywhere in the tree, fails the parse.

`require_up_to_date` is the one key kept accepted on purpose: it named
GitHub's strict required-checks mode, which is exactly what `base_freshness:
auto` computes to on every repository where the retired key could have been
set. `BranchProtection.RequireUpToDate` is an input-only field — `Parse`
translates it onto `BaseFreshness` and clears it, so the resolved spec never
carries two spellings of the same guarantee.

**Before adopting this release**, run `gt repo check` against your fleet.
Any repository whose `.gt-repo.yaml` carries a key gt does not recognize —
including one retired by an earlier release, `require_up_to_date` aside —
starts failing where it passed before.

## The clearance workflow rename

`gt's` own repository resolves its upstream reusable workflow ref from the
rendered filename directly: `pipeline.go` builds `gt-lydite-clearance.yml`'s
`uses:` target from the literal filename, which has to match a real
`reusable-<name>.yml` gt's own repository publishes. The old name,
`lydite-clearance.yml`, also exists inside `lydite/actions`, and the
collision made it ambiguous which repository's workflow a `uses:` reference
of that shape was resolving to.

`gt repo fleet sync` rewrites a governed repository's rendered file from
`lydite-clearance.yml` to `gt-lydite-clearance.yml`. Nothing here removes
the old file on its own — an unmanaged file that gt no longer writes is left
in place until something deletes it.

## Coverage baseline

`reusable-lydite-baseline.yml` records a coverage baseline on every push to
the default branch of a repository with `lydite.coverage: true`. It sits in
the same `{{- if .Lydite }}` template region as the `lydite:` job itself, but
gated on its own `{{- if .LyditeCoverage }}` — `lydite` enabled does not by
itself mean coverage is on, and a repository with coverage off had nothing
here to measure. The baseline job holds `contents: write`; a repository that
never asked for coverage never grants it.

## Relay identity

```yaml
lydite:
  enabled: true
  relay: octobot   # optional — omit it to use the fleet default
```

`Lydite.Relay` forwards as the `relay` input on both
`reusable-lydite.yml` (the scan gate) and `gt-lydite-clearance.yml` (the
`/lydite clear` responder). Left empty, `gt repo settings apply` writes
`GT_LYDITE_RELAY` as a repository Actions variable — the same value,
`https://pr.lydite.org`, across every lydite-enabled repository in the
fleet — and both reusable workflows fall back to `vars.GT_LYDITE_RELAY`
whenever `relay` comes through empty:

```yaml
relay: ${{ inputs.relay != '' && inputs.relay || vars.GT_LYDITE_RELAY }}
```

The variable and the fallback are two separate changes that only take effect
together: writing `GT_LYDITE_RELAY` without the reusable workflows reading
it left the variable sitting unused, and the reusable workflows reading a
variable `gt repo settings apply` had not yet written would have fallen
through to nothing. Both are in this release, so a repository that runs
`gt repo settings apply` against synced `@v2` workflows gets the default
relay identity without setting `relay:` itself.

`gt repo settings apply` lists a repository's Actions variables and compares
by value before writing — creating the variable if absent, patching it in
place if present with a different value, and leaving it alone if it already
matches. It lists rather than fetching the variable by name, because the
underlying `gh api` call collapses every non-zero exit into one error
string, and reading "absent" out of a broken credential would create the
variable's stale absence report right past a token failure.

## Upgrading from v2.0.0

```sh
gt update
gt repo fleet sync             # rewrites lydite-clearance.yml to
                                # gt-lydite-clearance.yml, adds the coverage
                                # baseline stage where lydite.coverage is on
gt repo settings apply         # writes GT_LYDITE_RELAY where lydite is
                                # enabled and relay is unset
```

Run `gt repo check` first if you are not already doing so as part of the
fleet sync. A `.gt-repo.yaml` that parsed clean on v2.0.0 can now fail to
parse — the strict decode is the one change here that can turn a passing
check into a failing one without anything else on the repository having
moved.
