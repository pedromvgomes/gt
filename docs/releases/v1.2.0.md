## Highlights

- **A repository can turn the coverage gate off.** `bulwark.coverage: false`, for
  a repository with nothing bulwark can measure. Previously the only options
  were a gate that fails outright or one that publishes a number about nothing.

## `bulwark.coverage`

```yaml
bulwark:
  enabled: true
  coverage: false   # default true
```

boma is the case that produced it: its unit suite is shell and its end-to-end
suite drives containers, so there is no Go, Rust or TypeScript source for
bulwark to measure. Neither existing setting could say that.

| `coverage.source` | what happens with nothing to measure |
|---|---|
| `report` | bulwark **exits** — it was told to read a report nothing writes |
| `run` | the gate resolves a baseline for languages that do not exist, and publishes a coverage result on every run |

The second is the dangerous one. A number that means nothing is a number people
stop reading — **including on the repositories where it means something**. That
is how `76.2% (baseline 0.7%)` sat in every gt run's log until someone looked.

Setting it to `false` passes `run-coverage` through to the bulwark action, an
input it already had. gt simply never used it.

`.bulwark.yml` is no longer scaffolded when the gate is off: that file exists to
declare where coverage comes from, and with the gate off there is no such
question. gt never deletes a scaffold, so a repository that wants the file for
bulwark's other settings — language excludes, the TypeScript linter choice — can
keep or add it.

## Who wants this

Repositories whose tests do not produce a coverage profile bulwark can read:
shell suites, container-driven end-to-end tests, and infrastructure repositories
that are configuration rather than code. In this fleet that is `boma` today and
`wardnet-infrastructure` next.

**The scan is unaffected.** Turning coverage off does not turn scanning off —
gosec, govulncheck and semgrep still run, and semgrep reads shell and Python,
which is most of what a repository like this contains.

## Upgrading

Nothing to pin: governed repositories track `@v1`, which this release moves.

Nothing changes for a repository that does not set it. `coverage` defaults to
true and is deliberately not written into the rendered orchestrator when on — a
`with:` block that exists only to restate a default is noise in every file that
carries it.
