## Highlights

- **Every governed repository now gets an ordering guarantee on its default
  branch.** A pull request must be built against the branch it will actually
  land on, not the one it was opened from — the one guarantee neither the
  required check nor the validated-tree attestation can give.
- **The guarantee is named; the mechanism is computed.** `base_freshness`
  replaces `require_up_to_date`. Under the default `auto`, gt establishes
  whether the repository can hold a merge queue and picks one — a queue where
  possible, `strict` where not.
- **`gt set-auth` can pin arbitrary environment variables per repository**, so
  tooling launched from a checkout resolves the same credentials regardless of
  which shell started it. The motivating case is coding-agent CLIs, but gt
  attaches no meaning to what it exports.
- **This release changes rendering.** The `merge_group` trigger is now
  unconditional in `ci-orchestration.yml`, so every governed repository is
  drifted until it syncs. Unlike v1.6.0, this one wants a fleet sync.

## What was wrong

Two pull requests can touch disjoint files — one adding a caller, the other
bumping the API it calls — be individually green, be conflict-free to git, and
break the default branch the moment the second lands.

Nothing gt had could catch that. The required check and the attestation both
answer "did this pass?" about a tree that was already fixed. Neither answers
"does it still pass against what landed while it sat open?". gt's own `main`
broke exactly this way, which is what prompted the release.

`require_up_to_date` existed and would have prevented it, but it named one
mechanism, defaulted off, and so was set nowhere.

## What changed

```yaml
settings:
  branch_protection:
    base_freshness: auto   # auto | queue | strict | none
```

`auto` is the default and needs no entry in your spec.

The naming matters more than it looks. GitHub offers two mechanisms for this
guarantee, and **which one a repository may use is a fact about the repository
rather than a preference**: merge queues require an organization-owned public
repository. Naming the mechanism would have meant every user-owned repo — gt's
own among them — either failing to apply the setting or silently getting
nothing. Naming the guarantee lets `auto` establish the fact and pick:

| repository | mechanism under `auto` |
|---|---|
| organization-owned, public | merge queue |
| everything else | `strict` (GitHub's "require branches to be up to date") |

The two are never applied together. Doing so would pay the rebase churn *and*
the queue latency for a single guarantee, so they are branches of one decision
rather than two switches.

`queue` and `strict` demand a specific mechanism. `queue` **reports** rather
than silently substituting where the repository cannot have one — asking for a
mechanism and quietly getting another is worth being told about. `none` gives
up the guarantee.

## The ordering that makes it safe

A merge queue only works if the required check reports on `merge_group` events,
and `ci-gate` only does that once the synced orchestrator has landed on the
default branch. Applying the rule first would put every pull request into a
queue that can never build it — and the governance stage that would have said
so is itself inside the check that no longer reports, so the failure hides
itself.

So `gt repo settings apply` **withholds the queue rule until it has read the
`merge_group` trigger off the default branch**. That is why the trigger is now
rendered unconditionally, including in repositories that can never hold a
queue: the file is ready before the rule that needs it. An unused trigger costs
nothing.

Withholding is not dismantling. A repository whose queue already works, hitting
a transient probe failure or a momentarily unreadable workflow, comes out of
apply with the queue it had — and, as of this release, with the `strict` policy
it had too. A blip postpones the decision; it never removes the protection.

## Environment profiles

A coding-agent CLI resolves its credentials from a directory named by an
environment variable — `CLAUDE_CONFIG_DIR` for Claude Code, `CODEX_HOME` for
Codex. Anything that shells out to one inherits whatever the launching shell
exported, so the same command in the same worktree can authenticate as a
different account depending on which terminal started it, with no warning.

`gt set-auth` already pinned `GH_TOKEN` to a named `gh` user for exactly this
reason. Profiles extend that to any other variable:

```yaml
# ~/.config/gt/config.yaml
profiles:
  - name: work
    match: ["github.com:acme/*"]
    env:
      CLAUDE_CONFIG_DIR: ~/.claude
  - name: personal
    env:
      CLAUDE_CONFIG_DIR: ~/.claude-personal
      CODEX_HOME: ~/.codex-personal
```

gt attaches no meaning to the names or the values. It exports what you list and
nothing else, so a CLI gt has never heard of needs no gt release — just another
entry under `env`. This is why there is no `--claude-config-dir` flag, which
would have fixed one provider and left the identical failure one variable over.

Selection is first-match-wins against the repository's `origin` URL, using the
same glob syntax as setup templates. A profile with no `match` never applies on
its own; select it with `--profile <name>`. The mapping lives in the user
config rather than in `.envrc`, because `.envrc` is not committed and a fresh
clone has to re-derive it from something that survives.

**Nothing is opt-out by default.** A repository matching no profile produces an
`.envrc` byte-identical to what gt wrote before profiles existed, so running
`gt set-auth` across an existing fleet rewrites none of them.

There is no prompt. `set-auth` runs from clone hooks and CI where a question is
a hang, and the config already holds the answer.

## Also in this release

- **An absorbed rule no longer reads as drift.** A rule gt folded into its own
  ruleset on a previous apply — wardnet's `code_quality` is the live case —
  left `gt repo settings diff` permanently dirty, describing a removal that
  never happened.
- **A paused ruleset no longer loses its absorbed rules.** Re-activating gt's
  own ruleset dropped every rule it had previously absorbed, on a run whose
  only reported change was the enforcement flag.
- **The owned rule set is fixed rather than derived.** Deriving it from the
  rendered output made `required_status_checks` look unmanaged whenever
  `pipeline.ci` was disabled, so apply carried a live `ci-gate` requirement
  through and the repository kept the very gate the omission exists to remove.
- **Stage scaffolds declare `packages: read`.** A called workflow may only
  narrow what its caller grants, so a stage that omitted the scope broke any
  step resolving a private `@scope` dependency — and the failure named the
  registry rather than the file.
- `gt clone --profile` rejects an unknown name before the clone starts, rather
  than after the folder exists and the obvious retry fails differently.

## Upgrading

**This release wants a fleet sync**, unlike v1.6.0. `merge_group` is now
rendered unconditionally, so every governed repository's `ci-orchestration.yml`
is drifted:

```sh
gt repo fleet check --owner <name>     # see the damage
gt repo fleet sync  --owner <name>     # a PR per repo
```

Then, once each repository's orchestrator has landed on its default branch:

```sh
gt repo settings apply
```

Order matters, and gt enforces it rather than trusting you to remember: apply
withholds the queue rule until the trigger is live on the default branch. Run
it before the sync lands and you get the `strict` fallback or a deferral, never
a queue nothing can build for.

`base_freshness` needs no action. A spec still carrying `require_up_to_date`
parses to `auto` — the key is ignored, not rejected — which on the repositories
where it could have been set computes to `strict` anyway.

Environment profiles need no action either. With no `profiles:` in your config,
every `.envrc` gt writes is byte-for-byte what it wrote on v1.6.0.
