## Highlights

- **A pipeline stage can now be granted permissions beyond the baseline**, via
  `pipeline.ci.stage_permissions` (and `pipeline.cd.stage_permissions`). The
  orchestrator template used to say "a stage needing more than this is a gt
  change"; this is that change.
- **It exists because the failure it prevents is silent.** A leaf that needs a
  scope the baseline withholds does not fail loudly when it is migrated — it
  keeps passing while quietly no longer doing the thing. wardnet is the
  repository that surfaced it, and could not have onboarded without this.
- **No repository's behaviour changes.** The baseline is untouched and the new
  field is `omitempty`. The rendered *comments* do change, so the next fleet
  sync is a comment-only diff — the one thing to expect from this release.

## What was wrong

Every stage job in a rendered orchestrator was granted a fixed baseline:

```yaml
permissions:
  contents: read
  packages: read     # contents: write + packages: write for CD
```

GitHub allows a called workflow to *narrow* what its caller grants, never to
widen it. So a stage's baseline is a ceiling: a leaf that needs
`security-events: write` cannot ask for it back, and there was no way to say so
in the spec.

That was liveable while every migrated leaf fit inside the baseline. wardnet
does not. Two of its eight `pr.yml` leaves need more:

| leaf | needs | for |
|---|---|---|
| `build-daemon` | `security-events: write` | `codeql-action/upload-sarif`, uploading clippy SARIF |
| `tests-e2e` | `packages: write` | `--cache-to type=registry,...buildcache` |

The important part is what migrating them as-is would have looked like. Neither
call fails the job when the permission is missing. The SARIF upload and the
cache export would simply have stopped happening, on a pipeline that stayed
green — which is exactly the "passes while asserting nothing" defect this whole
subsystem exists to remove.

The alternatives were both bad: migrate and lose two capabilities silently, or
set `pipeline.ci.enabled: false` and leave wardnet off the CI pipeline
indefinitely.

## What changed

A stage may be widened by name:

```yaml
pipeline:
  ci:
    stages: [preflight, build, test, end2end]
    stage_permissions:
      build:
        security-events: write   # codeql-action/upload-sarif
      end2end:
        packages: write          # --cache-to type=registry
```

- **Merged over the baseline.** A named scope is raised — `packages: read` →
  `write` — and every scope not named is left alone.
- **Strictly per-stage.** Only the stage named is widened; a grant never
  reaches its siblings. `test` above still holds exactly `contents: read` +
  `packages: read`.
- **Available for CD too**, since `cd-orchestration` carried the same "is a gt
  change today" note.

The rendered file explains a widened stage differently from a baseline one, so
a job holding a write scope says why it has it and which spec key put it there.
The grant is reviewable in the diff rather than implied by a template.

## The scope vocabulary is enumerated, deliberately

Stage names, permission scopes and levels are all validated at sync time. The
scope list is a closed vocabulary rather than a passthrough, and that is the
load-bearing decision:

**GitHub ignores an unknown permission scope silently.** A plausible typo —
`code-scanning: write` instead of `security-events: write` — would render a job
that reads as widened, passes review, and then fails at the single API call it
was meant to permit, long after anyone is looking at the diff. Rejecting it at
sync time turns a silent runtime failure into a spec error.

Also rejected: a grant naming a stage the pipeline does not run, an invalid
level, an empty scope map, and any grant while that pipeline is disabled.

Scopes render sorted. Go randomises map iteration, so an unsorted render would
produce a fresh diff on every sync and make `gt repo check` flap between
compliant and drifted with no change to the spec.

## Upgrading

**Expect one comment-only diff per repository, and nothing else.**

The baseline is unchanged and `stage_permissions` is `omitempty`, so no
`.gt-repo.yaml` gains a key and no rendered directive moves. Verified by
rendering every managed file on v1.4.0 and on this release and diffing: with
comments stripped, both orchestrators are byte-identical.

What does change is the comment above each stage's `permissions:` block, which
now points at `stage_permissions` instead of saying a wider stage is a gt
change. gt's own re-render in #58 is the whole shape of it:

```diff
     # Read-only, so granting it where it is unused costs nothing. A stage
-    # needing more than this is a gt change.
+    # needing more says so in pipeline.ci.stage_permissions.
```

Three lines per orchestrator. `gt repo check` will report
`ci-orchestration.yml` as drifted until each repository re-renders, so this
release wants a `gt repo fleet sync` — unlike v1.4.0, which needed nothing.

## Details worth knowing

- **gt governs itself**, so an orchestrator-template change drifts gt's own
  committed workflow and fails its `governance` stage. Any future template edit
  has to re-render `.github/workflows/ci-orchestration.yml` in the same PR.
- **An unversioned build refuses to sync a v1-rendered repository.** Running a
  `dev` binary against gt itself stops with "syncing would repoint its
  workflows from v1 to v0" rather than doing it. Build with
  `-ldflags "-X main.version=vX.Y.Z"` when rendering.
- gt's own `gt_version` stays `v1.0.0`. It has not moved since #31, and a
  template change is not what should move it.
