## Highlights

- **Repos can declare their own setup.** Commit a `.gt.yaml` with a `setup:`
  block into the repository tree, and gt runs those templates automatically
  after `gt clone` (in the default-branch checkout) and after `gt wt add` (in
  the new worktree). No per-machine global config needed — the initialization
  travels with the repo. This is what makes a toolkit like
  [`agentic-toolkit`](https://github.com/pedromvgomes/agentic-toolkit)
  (`agtk sync`) initialize on the root checkout *and* every new worktree.
- **`GT_SETUP_PHASE`** tells a template what triggered it (`clone`,
  `worktree`, or `manual`), so a single template can branch — e.g. pass
  `agtk sync --source` only on clone and a plain `agtk sync` inside worktrees.

## Repo-declared setup templates

A repo's committed `.gt.yaml` may now define `setup.templates`, the same shape
as the global config, except they run **unconditionally** for that repo (no
`match` globs required):

```yaml
setup:
  templates:
    - name: agentic-toolkit
      run: |
        set -e
        command -v agtk >/dev/null 2>&1 || \
          curl -fsSL https://raw.githubusercontent.com/pedromvgomes/agentic-toolkit/main/install.sh | sh
        if [ "$GT_SETUP_PHASE" = "worktree" ]; then
          agtk sync
        else
          agtk sync --source "${GT_ROOT}/${GT_DEFAULT_BRANCH}"
        fi
```

When both the global config and a repo's `.gt.yaml` define a template, the
matched global templates run first and repo templates are appended; a repo
template overrides a global one with the same name.

`gt wt add` gains `--no-setup`, `--yes`, `--show-setup`, and `--dry-run-setup`,
mirroring `gt clone`.

## Safety

Templates committed in a cloned repo are shell controlled by whoever authored
that repo, so they are treated as **untrusted**:

- Without a TTY, gt **refuses to auto-run** repo-declared templates unless
  `--yes` is passed explicitly — cloning an untrusted repo in CI no longer
  executes its setup silently.
- Interactively, gt prints a warning naming `.gt.yaml` before the
  confirmation prompt.

Templates from your own global config remain trusted and keep their existing
non-interactive auto-run.

## Other changes

- `gt wt add` resolves the default branch from the local `origin/HEAD` symref
  instead of a `git remote show origin` network round-trip (with a network
  fallback only when that ref is absent).

## Upgrading

```sh
gt update
```

No config migration needed. Existing global setup templates are unaffected; the
new behavior only activates when a repo ships its own `.gt.yaml`.
