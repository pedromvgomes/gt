## Highlights

- **`bulwark` is gone.** The `bulwark:` spec key, the `Bulwark` Go type, the
  `BulwarkReferralContext` constant, and `reusable-bulwark.yml` no longer
  exist anywhere in this repository — not even as a compatibility shim. Every
  governed repository configures the gate under `lydite:` now, and a manifest
  still carrying `bulwark:` is silently ignored by non-strict YAML parsing,
  the same as any other key gt does not recognize.
- **The gate runs lydite's full pipeline**, not a hand-rolled forward to a
  third-party action. `reusable-lydite.yml` forwards entirely to
  `lydite/actions/.github/workflows/lydite.yml@v1` — referral, scan, test and
  publish, orchestrated as one call.
- **A referral now actually blocks merge.** Branch protection requires a
  second status, `lydite/referral`, alongside `ci-gate`. A "refer" verdict
  never fails the gate job itself; without this, nothing stopped a referred
  pull request from merging anyway.
- **`/lydite clear` now has something listening for it.** A new
  `lydite-clearance.yml`, triggered on `issue_comment` rather than
  `pull_request`, answers a `/lydite` comment on a pull request and is what
  actually clears a referral. Without it, the referral check's own
  instructions — "comment `/lydite clear` to resolve" — described a path that
  did nothing.
- **This is v2, not v1.8, because it breaks `@v1`.** Every repository still
  pinned to `pedromvgomes/gt/.github/workflows/reusable-bulwark.yml@v1` keeps
  working, unaffected — `v1` is not moving. A repository adopts this release,
  and everything above, by deliberately upgrading its `gt` and running
  `gt repo sync`, the same as the v0 → v1 jump.

## Why full removal, not another shim

`reusable-bulwark.yml` already carried one compatibility shim, kept expressly
so a filename rename would not break every already-governed repository at
once. Keeping a second shim on top of that — one reusable workflow forwarding
to another forwarding to lydite's own pipeline — would have meant carrying
dead indirection indefinitely, for a name every governed repository was
already migrating away from. A major version exists precisely for a change
this shape: repositories that have not yet moved are not silently broken,
and a repository that adopts it accepts the whole change, not a patched-over
half of it.

## The referral gate

```json
{"required_status_checks": [{"context": "ci-gate"}, {"context": "lydite/referral"}]}
```

`lydite/referral` is not scoped to a verified publisher's `integration_id`
yet — anything with repo write access could currently satisfy it without
going through `/lydite clear`. There is no App identity to scope to: checked
directly against `lydite/lydite`, the referral status and its clearance are
both published under the plain per-run `GITHUB_TOKEN` today, not any
`lydite`/`lydite-cicd-bot`/`lydite-dashboard` App. Scoping the check to a
nonexistent identity would create a required check nothing could ever
satisfy, which is worse than the current gap. Tracked separately, blocked on
`lydite/lydite` authenticating that path as an App first.

## Clearing a referral

`lydite-clearance.yml` is deliberately its own workflow file, never a job
folded into `ci-orchestration.yml`. An `issue_comment` run always executes
the *default branch's* own copy of every workflow file, never the pull
request's — that property is what makes it safe for the job to hold
`statuses: write` at all, since the logic deciding a clearance can never be
something the pull request under review gets to edit. Mixing that trigger
into `ci-orchestration.yml` would also run every other job there — build,
lint, the whole pipeline — on every PR comment.

It forwards only a `dir` input for now. `lydite-version` and `relay` stay
unexposed: with no App identity publishing lydite's statuses yet, there is no
relay to hand it, so every governed repository answers a clearance under
`github-actions[bot]` until one exists.

## Upgrading from v1.x

`v1` is untouched — nothing breaks by staying on it, and nothing about this
release reaches a repository that does not ask for it.

To adopt lydite's full pipeline and the referral gate:

```sh
gt update              # or your package manager's usual upgrade path
gt repo sync           # rewrites reusable workflow refs from @v1 to @v2
```

Then, once `ci-orchestration.yml` and the new `lydite-clearance.yml` have
landed on the default branch:

```sh
gt repo settings apply
```

Ordering matters here the same way it did for `base_freshness` in v1.7.0:
`lydite/referral` has to exist as a check before it can be required, and
`lydite-clearance.yml` has to be on the default branch before a
`/lydite clear` comment can do anything — `issue_comment` runs the default
branch's copy, never the pull request's.

A manifest with a `bulwark:` block and no `lydite:` of its own parses to the
default spec on this release — `lydite` enabled, at the repository root, with
coverage on. Any customization held under the old key (disabled, a non-root
`dir`, coverage off) needs restating under `lydite:` before syncing, or it is
silently dropped rather than carried over.
