## Highlights

- **`.gt-repo.yaml` records decisions, not the resolved configuration.** `sync`
  writes only what differs from gt's defaults; everything absent follows gt and
  keeps following it. agentic-toolkit's file went from 74 lines to 5 lines of
  actual configuration.
- **This was a bug in the propagation mechanism, not in the formatting.** A
  repository that spells out a default has silently stopped tracking it, so
  changing an opinion in gt would have reached none of them.
- **`check` reports a file that restates defaults as drift**, so the gate
  catches it and the weekly in-repo sync slims it without anyone cloning eleven
  repositories.

## What was wrong

`gt repo sync` serialised the **fully resolved** spec. Every governed
repository therefore had all ~25 of gt's defaults written out explicitly:

```yaml
settings:
  merge:
    squash: true
    merge_commit: false
    rebase: false
    delete_branch_on_merge: true
    squash_title: pr_title
    squash_message: blank
  branch_protection:
    branch: main
    required_approvals: 0
    require_up_to_date: false
    dismiss_stale_reviews: true
    require_thread_resolution: true
    require_code_owner_review: false
    require_last_push_approval: false
```

None of that is a decision. It is gt's opinion, copied into a file that now
outranks it.

That is the whole problem. `gt repo` exists so shared policy propagates: the
[v1.0.0 notes](v1.0.0.md) describe three mechanisms for getting a change to
every repository without editing each one. Writing the resolved spec disabled
one of them. Changing a default in gt would have reached **nobody**, because
all eleven files already stated the old value — and nothing would have
reported it, since every repository was, by its own file, compliant.

## What is written now

```yaml
gt_version: 1.3.0
dependabot:
  - ecosystem: github-actions
    directory: /
  - ecosystem: gomod
    directory: /
pipeline:
  ci:
    stages: [preflight, build, test]
  cd:
    enabled: false
```

Four decisions, and they read as decisions. `gt repo config` still prints the
resolved spec with every default applied — it is what gt's own workflows
consume, and the file header now points at it.

Nothing about overriding changes. Any value that differs from the default is
kept, **including a `false` against a default of `true`**: pruning compares
against `Default()`, not against the Go zero value. Getting that backwards
would have silently switched `dependabot_auto_merge` and
`conventional_commits` back on wherever they had been turned off, so there is
a test pinning it.

## Upgrading

Safe, because `repospec.Parse` already layered the file over `Default()` — a
pruned file and a spelled-out one resolve to the same spec. Verified on
agentic-toolkit and on gt itself: `gt repo config` is byte-identical before and
after.

Your repositories will report drift until they are re-synced. That is
deliberate; it is the signal that carries the fix. Either run `gt repo sync`
locally, or wait for the weekly in-repo sync job to open the PR — it now slims
the spec even under `--skip-workflows`, which is the mode it runs in.

## Details worth knowing

Three things had to change for this to reach a repository at all, and each was
its own trap:

- **`check` treats a restated default as drift** (`Report.SpecStale`). Without
  it the gate stays green on a file that has stopped tracking gt.
- **`sync` no longer short-circuits on `len(drifted) == 0`.** Every managed file
  can be byte-correct while the spec still pins defaults. That state was
  otherwise unfixable — sync would print "Nothing to write" and exit.
- **`--skip-workflows` slims the spec too.** That is the mode the weekly in-repo
  job runs in, so skipping it there meant the fix could only ever arrive by
  hand, in eleven repositories. It still refuses to stamp `gt_version`, which
  is the one claim a run that did not render the workflow files cannot make.

Pruning walks `yaml.Node`s rather than a `map[string]any`, because `yaml.v3`
emits struct fields in declaration order but map keys sorted — a map-based
implementation would have reshuffled every file into an unreadable diff on
first sync. A nested struct with one override keeps that field and drops its
siblings, so `required_approvals: 1` does not drag the other six protection
settings along with it.
