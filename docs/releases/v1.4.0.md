## Highlights

- **bulwark's stage installs the toolchain a repository declares, and warms its
  caches, before scanning.** Without it the stage ran on whatever Go the runner
  happened to ship, with a cold module and build cache. That is survivable on a
  small repository and fatal on a large one: inforge's scan was reclaimed by the
  runner three times running, always mid-gosec.
- **This was a regression introduced by adopting the stage, not a bulwark bug.**
  Every hand-rolled bulwark job set the toolchain up before calling the action.
  Moving the job into gt's reusable workflow dropped that step.
- **gt tracks `wardnet/bulwark@v2`.** Nothing changes today — `action.yml` is
  byte-identical across `v1.9.0..v2.0.0` — but `v1` froze at 1.9.0 the moment
  2.0.0 shipped, so staying on it would have pinned the wrapper there forever
  while the binary it wraps kept moving.

## What was wrong

bulwark provisions a language toolchain when the ambient one does not satisfy
what a repository declares. It cannot cache: it is a composite action, so
`actions/cache` is out of reach. Every run therefore re-downloaded the
dependency tree and compiled it cold.

That went unnoticed because of who had migrated. The only Go repositories using
the stage were gt and bulwark:

| | `go.sum` | `require` | bulwark stage |
|---|---|---|---|
| gt | 17 | 6 | passes |
| bulwark | 17 | 6 | passes |
| inforge | 417 | 144 | killed, three times |

On six requires, gosec never approaches the runner's limits. On inforge it dies
loading the Pulumi-heavy packages, at four and a half minutes, well inside the
thirty-minute timeout.

The controlled comparison is inforge's own pipeline. Same repository, same
gosec, same package graph, passing in 3m32s — from a job whose only relevant
difference was `setup-go` with `cache: true`.

## What changed

`reusable-bulwark.yml` detects the ecosystems under `dir` and sets each one up
before calling bulwark:

- **Go** — `setup-go` with `go-version-file` pointed at the `go.mod` it found,
  and `cache: true`. Reading the repository's own file rather than restating a
  version is what keeps this from becoming another place that drifts.
- **Rust** — `Swatinem/rust-cache`, scoped to the crate directory. No toolchain
  action: the runners ship rustup, which honours a `rust-toolchain.toml`.
- **Node** — `setup-node`, with the cache enabled for npm and pnpm.

Detection walks from `dir` using the same skip set bulwark's own walk uses, so a
vendored manifest cannot decide an ecosystem bulwark will never scan.

The two halves are complementary rather than competing. The caller installs what
the repository declares; bulwark's probe then finds the ambient toolchain
satisfactory and provisions nothing. It says so out loud:

```
rust: using ambient cargo 1.97.1 (satisfies 1.96 from daemon/rust-toolchain.toml)
```

## Two things that only came out of testing

Neither would have survived review by inspection, and both broke the gate
*before* bulwark ran — the worst place to fail, because a security stage that
dies during setup looks the same as one that found something.

- `setup-node` resolves `cache-dependency-path` against the workspace root. A
  lockfile anywhere below it — inforge keeps a Docusaurus site in `website/` —
  fails the action outright with "Dependencies lock file is not found". The
  lockfile actually found is now named explicitly.
- **yarn is detected but deliberately left uncached.** `setup-node` asks the
  *global* yarn where its cache lives, and a project on Berry
  (`"packageManager": "yarn@4"`) makes the runner's global Yarn 1.22 refuse,
  exiting non-zero. Skipping the cache costs nothing bulwark measures; getting
  it wrong costs the entire scan.

## Upgrading

Nothing to do per repository. Callers pin gt's moving major, so this arrives
when `v1` advances — no file changes, no `gt repo fleet sync`, and `gt repo
check` stays green throughout.

Verified on both compiled ecosystems, which is where the cost is: Go on inforge,
where the scan goes from three consecutive kills to passing in 3m22s, and Rust
on wardnet with `dir: source`, where detection resolved the nested crate at
`source/daemon` and the scan completed clean.
